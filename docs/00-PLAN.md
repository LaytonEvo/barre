# Barre By Kelly — build plan (M0)

**Status:** proposed, awaiting Layton's approval. No application code written yet.

---

## 1. What we're building

A production website and members' platform doing three jobs:

1. **Convert** — local search → intro offer → first booking, with as little friction as possible.
2. **Run the business** — accounts, waivers, booking, cancellations, packs, memberships, payments, with zero manual admin from Kelly.
3. **Retain** — at-home video library, reminders, win-back automation.

### The one architectural rule that matters

Kelly teaches 3 classes a week today and will scale to more classes, more venues, more
instructors. **Nothing is hard-coded to one of anything.** Concretely:

- No `INSTRUCTOR_NAME` constant; `instructors` is a table and every session references one.
- No hard-coded timetable; sessions are generated from `schedule_templates` by a cron job.
- No magic numbers for policy. Cancellation window, booking window, waitlist cutoff,
  penalties, reminder timings and credit rollover all live in a `settings` table, read
  through `/lib/policy`. **The policy text shown to members is rendered from the same
  values that the booking logic enforces**, so the copy can never drift from the code.
- Prices and products are rows synced to Stripe, not constants.

### Three things worth flagging before I start

1. **Timezone.** All timestamps stored as `timestamptz` (UTC). Class times are authored in
   `Europe/London` and converted on write. This matters twice a year: a template saying
   "Monday 09:30" must still mean 09:30 local after the clocks change. Sessions are
   generated by applying the local wall-clock time in the venue's timezone, not by adding
   168 hours. I'll cover this with a BST/GMT boundary test.
2. **Money is always integer pence.** No floats anywhere near a price.
3. **Scheduled jobs run on Supabase `pg_cron`** (decided at M1). Vercel Cron on the Hobby plan
   only fires once a day, which cannot do a 2-hour class reminder; Pro would cost ~$20/mo for
   something the database can do for nothing. The jobs are database-centric anyway — session
   generation, credit expiry, reminder queueing — so they live next to the data.

### Why this order

M4 lands before M5 on purpose. The booking engine needs entitlements to exist before it
can check them, and the credit ledger is the thing most likely to reveal a modelling
mistake. Building payments against a bare schema and then layering booking on top is
cheaper than retrofitting a ledger under a working booking flow.

## 4. The three places this gets hard

Most of this build is well-trodden CRUD. Three parts are not, and they get
disproportionate attention and tests.

### 4.1 No overbooking (M5)

Naive `SELECT count(*) ... then INSERT` loses races and double-books a full class. Booking
runs as one Postgres function:

```
book_session(p_session_id, p_user_id):
  SELECT ... FROM class_sessions WHERE id = p_session_id FOR UPDATE;  -- serialise
  assert status = 'scheduled'
  assert starts_at > now() and within booking window
  assert current waiver signed and PAR-Q complete
  assert no existing active booking for this user
  assert active bookings < capacity        -- safe: row is locked
  pick the soonest-expiring unexpired credit (FIFO)
  INSERT booking; INSERT credit_ledger (booking_debit)   -- same transaction
```

Plus a partial unique index `(session_id, user_id) WHERE status IN ('booked','attended')`
as a belt-and-braces guard against the same member double-booking.

Acceptance test 5 fires 20 concurrent bookings at a 10-space class and asserts exactly 10
succeed and 10 are offered the waitlist.

### 4.2 The credit ledger (M4)

`credit_ledger` is **append-only** — a database trigger rejects `UPDATE` and `DELETE`.
Balances are never stored; they're derived. Entry kinds: `purchase`, `booking_debit`,
`cancel_refund`, `late_cancel_forfeit`, `expiry`, `admin_adjustment` (reason + admin id
required), `voucher_redeem`, `membership_grant`.

Consumption is FIFO by expiry, so the credit about to die is spent first. A refund restores
the credit **with its original expiry**, not a fresh 90 days — otherwise members farm
extensions by booking and cancelling. Unit tests cover every kind, plus the expiry edges.

### 4.3 Webhooks as the source of truth (M4)

Nothing is fulfilled on a Checkout redirect — users close tabs, and a redirect is not proof
of payment. Credits are granted only by a signature-verified webhook. Every handler is
idempotent via a `stripe_events` table keyed on the Stripe event id, because Stripe retries
and will deliver the same event twice.

## 5. Testing posture

- **Unit (Vitest):** every ledger path, policy resolution from settings, FIFO expiry,
  intro-offer eligibility, waitlist promotion ordering, BST/GMT session generation.
- **Integration:** booking RPC under concurrency; webhook idempotency on replay.
- **RLS:** a test per table asserting member A cannot read member B's rows, and that health
  data is invisible to the `member` role entirely. Run as a real authenticated client, not
  as service-role.
- **E2E (Playwright):** all 14 Section 14 scenarios, with the register/check-in flow run at
  a mobile viewport.
- **A11y:** axe in CI on every public route; manual keyboard pass before launch.
